# Product architecture

Who it is for: a builder, alone or in a small team, who mixes free, local and paid models and wants the most accepted work per
paid call without giving up control.

This document fixes the design. Each part says whether it **exists** (module and tests named) or is **to build** (interface given).
Nothing here has run with a real model yet; see *Open risks*.

## 1. The stack stays; three things change

Python standard library, React, Tauri and SQLite are right for a local app that drives other vendors' CLIs: the engine has no
dependencies, so it can ship as one small sidecar. What changes:

1. **One event log is the source of truth.** Today state lives in two SQLite files and several JSON files. One append-only
   `events` table with a sequence number; the board, the metrics and the live view are projections of it. The page subscribes
   from a cursor (`/api/events?after=<seq>`) and resumes without polling. *To build.*
2. **A cost ledger in honest units.** Per call: tokens in and out, seconds, and whether it was a paid call. Money appears only
   when the tool itself reports it. A subscription has no price per call, so the headline figure is *accepted at the first
   attempt per paid call*, not a currency. *To build; what each CLI reports must be read first.*
3. **The engine ships inside the app.** Without a bundled sidecar the first minute only works on the author's machine. Optional
   engines stay out of the bundle. *To build.*

## 2. The first 60 seconds

Sixty seconds is the time to a running team and the first live evidence, not the time to a finished mission.

| Second | Engine | Screen |
|---|---|---|
| 0–5 | Window paints at once; engine starts beside it | "Choose a folder" and a chip: engine starting |
| 5–15 | `detect(root)`: no model call | One row per tool: found, version, "sign-in not checked" |
| 5–25 | `missions(root)`: no model call, runs beside the detector | Three mission cards, the first one selected |
| 15–25 | `propose_team(detected)`: rules, not a model | Four seats, each with the reason it got that agent |
| 25–30 | One click writes the config (previewed) and starts the run | "Launch" |
| 30–60 | Scout reads, author starts in its worktree | The Run view, live |

### 2.1 Detector — `detect(root) -> dict` (to build, `caos_harness/detect.py`)

Probes in parallel, two seconds each, zero tokens: which of `claude`, `agy`, `codex`, `opencode`, `ollama` are on the PATH
(`desktop.ensure_user_path` first), their `--version`, the models Ollama lists on its local port, whether the folder is a git
repository with a commit, and the test command (see 2.3). It never checks a sign-in by calling a model: that is the existing
one-turn *Smoke*, on demand.

### 2.2 Seats — `propose_team(detected) -> dict` (to build)

| Seat | Rule |
|---|---|
| Scout | cheapest agent with file tools |
| Author | cheapest agent with an edit mode |
| Reviewer | a different tool family from the author; `cycle.pick_verifier` (exists) |
| Orchestrator | not used by a generated mission (its plan is a template); the paid agent otherwise |
| Escalation | the paid agent, used only on the third attempt (section 3.3) |

One family installed: the reviewer is another model of it and the card says "same family: weaker review". One model only: no
cycle; the app offers read-only missions and says why.

### 2.3 The first mission is generated by code — `missions(root) -> list[Mission]` (to build, `caos_harness/missions.py`)

A model is not asked what to do. Candidates come from signals a program can point at, and each carries its own proof:

| Rank | Signal | Mission | Acceptance |
|---|---|---|---|
| 1 | The test command fails now (run once, 45 s budget) | Make the named failing test pass | the test command exits 0 |
| 2 | A public function no test file mentions (symbol map vs. tests) | Add a test for `f` in `file:line` | tests pass, **and fail when the body of `f` is replaced by a raise** |
| 3 | A `TODO`/`FIXME` with a file and line | Resolve it | the test command exits 0 and the marker is gone |
| 4 | A command the README names that no script defines | Fix the document | the named command exists |
| 5 | Always | Map the repository and propose three improvements, each cited | every citation resolves to a file and line |

```
Mission = {id, kind: "edit" | "readonly", title, why, evidence: [{file, line, text}],
           task, criteria, verify: [argv] | null, expected_files: int}
```

Rules: an `edit` mission is offered only when `verify` is a real command; a folder without tests gets missions 4 and 5 and
"mission 0: write the first test". A mission becomes a fixed plan (scout → author → reviewer → gate), so launching it costs no
planning call. Rank 2's acceptance is the cycle checking that the new test can fail: a test that passes against a broken
function is rejected by code, not by opinion.

### 2.4 The Run view (to build)

- **Lanes**, one per agent, with state and its meter: tokens, seconds, paid calls.
- **Citations as chips** that open the file at the line. Only citations the code resolved are drawn.
- **Verdict strip**: the reviewer (who, what it found), the verify command (its real output and exit code), and the commit on
  `harness/landed` with "diff against your branch".
- **One headline**: accepted at the first attempt per paid call, with its interval once there is enough data.

What is different from an agent framework or a single-agent sandbox: it runs on the subscriptions and CLIs the builder already
has, across vendors; the first task is found by a program and comes with its proof; and nothing is integrated on an agent's word.

## 3. Verification

### 3.1 State machine

```
queued ─▶ scouted ─▶ delivered ─▶ reviewed ─▶ merged ─▶ verified ─▶ landed
                         ▲            │           │          │
                         └── returned ◀───────────┴──────────┘        (attempt + 1, findings attached)
                                  │
                                  └─▶ needs_human                     (third failure, or anything the code cannot decide)
```

| From | To | Condition | Exists |
|---|---|---|---|
| queued | scouted | brief checked by code, or no scout | `scout.py` |
| scouted | delivered | the author delivers in its own worktree | `orchestrator.py` |
| delivered | reviewed | another agent answered; the answer was checked | `cycle.cross_review` |
| reviewed (approve) | merged | three-way merge onto the branch tip is clean | `landed.integrate` |
| merged | verified | the verify command exits 0 on the merged tree | `landed.integrate` |
| verified | landed | the branch moved by compare-and-swap | `landed.integrate` |
| reviewed (reject, invalid, tampered) | returned | findings become the note | `cycle.run_cycle(auto_redo)` |
| merged (conflict) | returned | new worktree from `landed.rebase_point`; never resolved in place | to wire |
| verified (branch moved) | merged | retried once, automatically | to wire |
| returned (third time) | needs_human | always | to wire |

`cycle.run_cycle` still ends in `worktrees.land` (the project folder). Wiring it to `landed.integrate` is the first task.

### 3.2 Why there is no rollback code

The merge is computed without a working tree, the result is verified in a throwaway checkout, the commit is written from the
tree id that was checked out, and one `git update-ref <new> <old>` moves the branch. Either the branch points at the tree that
passed or it did not move. `landed.undo` takes a landing off the same way. The builder's branch, index and folder are never
written; taking the work is their own `git merge harness/landed`.

### 3.3 Pay only on failure

| Attempt | Author | Reviewer |
|---|---|---|
| 1 | cheapest with an edit mode | another family |
| 2 | the same, with the findings | the same reviewer |
| 3 | the paid agent, with both sets of findings | another family from *this* author |
| — | a person | |

The paid model is the exception path. The ledger shows how often it was needed. *To build on `run_cycle`.*

## 4. Skills that improve after a return

The contract is in [SKILL_IMPROVEMENT.md](SKILL_IMPROVEMENT.md); `skill_eval.validate_proposal` and `skill_eval.gate` exist. Two
additions keep a long trace from costing a paid model and a change from weakening a skill:

- **Two-level reading.** A free agent turns each returned task into one line with a literal quote; code drops any line whose
  quote is not in the recorded note. A cheap agent proposes one change from those lines. No paid model reads a trace.
- **Fixed rules.** A line of a skill that ends in `[fixed]` cannot be the anchor of `replace_rule` or `remove_rule`. One change
  per trial; a rejected trial restores the previous text and must reproduce its hash.

## 5. Invariants: how the system is kept from fooling itself

| # | Invariant | Check |
|---|---|---|
| 1 | The builder's branch, index and folder never move | `tests/test_landed.py`: HEAD, branch, status and on-disk tree identical |
| 2 | The branch only points at a tree that passed | `tests/test_landed.py`: what the verify command leaves behind cannot land |
| 3 | Nothing lands without a named reviewer and a verify command | `tests/test_landed.py` |
| 4 | A conflict is never resolved silently | `tests/test_landed.py`: the verify command does not even run |
| 5 | Two writers cannot overwrite each other | `tests/test_landed.py`: branch moved mid-verification; two landings at once |
| 6 | The reviewer is never the author and does not edit what it reviews | `tests/test_cycle.py` |
| 7 | The reviewer is measured against something it cannot see | `cycle.verifier_stats`: verdict against the verify result |
| 8 | A skill proposal quotes recorded returns | `tests/test_skill_eval_radar.py` |
| 9 | A generated test can fail | to build with mission rank 2 |
| 10 | The tests catch injected faults in the gate itself | six hand-made mutants of `landed.py` were caught; to add to `make mutation` |
| 11 | Every figure on screen is a count of events | to build with the event log; no estimate is drawn |

`landed.audit` re-reads the branch from git alone and flags any commit the harness did not write: the claim "only verified work
is on this branch" can be checked by someone who does not trust the app.

## 6. Open risks

- **No real model has gone through the cycle.** If the free models do not answer the review in the JSON asked for, every review
  is `invalid` and nothing lands. That fails safe and is useless. Measure it before building the Run view around it.
- **The guarantee is the builder's tests.** In a folder with weak tests "verified" means little. The team card must say so.
- **The ledger may only have tokens and seconds** for subscription CLIs, which weakens "quality per dollar" into "quality per
  paid call". That is the honest figure; the product should not pretend to more.
- **Mission rank 1 runs the builder's test command** during onboarding. It is their own command in their own folder, with a
  time budget, in a staging copy; it is still code execution before the first click and needs an explicit "run my tests" switch.
- **`landed.py` needs git 2.38 or later.**
